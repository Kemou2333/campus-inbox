# 长期运行与容量边界

本文件记录 2026-10-14 的源码与一次隔离短突发测试，不代表已发布、真机验收或公网承载保证。测试不访问真实账号内容，不调用 DeepSeek 或邮件，不修改生产数据库。

## 当前服务器

在实际服务器上读到：2 个逻辑 CPU、系统可见内存 1.575 GiB（约 1.58 GiB）、根文件系统约 39.01 GiB、空闲约 22.87 GiB。空闲量会随使用变化。购买套餐中的公网带宽和月流量没有从供应商控制台核对，不能用网卡标称速率或 localhost 测试猜测购买带宽。

部署结构是 HTTPS Nginx → 本机 Node 单进程 → SQLite。生产 Node 默认仅监听 `127.0.0.1:8787`，没有把 SQLite 或管理接口直接交给浏览器。`campus-inbox.service` 以独立系统用户运行、进程内存上限 256 MiB、最多 64 个系统任务；故障后五秒重启，并限制对系统目录的写入。安装器健康检查失败会切回上一版代码，用户状态目录独立保存，不随代码发布替换。

这台机器适合当前小规模文字应用。首先限制大家使用次数的是模型入口与预算，不能把 CPU、内存够用理解成大家能同时无限整理。

## 隔离容量测试

测试在实际服务器的随机临时目录中运行新源码，独立 SQLite 和虚构身份；HTTP 只监听随机 localhost 端口。临时进程通过 cgroup 限制为 **最多 128 MiB、最多 1 个 CPU、最长 15 秒**，没有重启生产服务。测试约 1.93 秒结束，峰值 RSS 约 88.1 MiB。这是短突发检查，未验证持续运行、真实外网、HTTPS、密码派生、大附件或真实模型。

每档 80 个操作，包含 40 次同步写入、20 次同步读取、20 次管理员元数据读取；三档合计 240 次操作全部成功，没有限流或格式拒绝。采用 21 个虚构账号，操作并发不等于独立在线人数。

| 同时进行的操作 | 中位延迟 p50 | p95 延迟 | 成功 |
| --- | ---: | ---: | ---: |
| 10 | 54.5 ms | 151.9 ms | 80 / 80 |
| 20 | 85.1 ms | 326.2 ms | 80 / 80 |
| 50 | 166.7 ms | 461.7 ms | 80 / 80 |

假模型验证中，第一条任务获得 202 云端接收确认，第二条不同原文收到 429 `SERVICE_BUSY`；只有一次假模型执行。真实模型、邮件调用及生产写入均为零。原始延迟分组、实际硬件、内存峰值、受测源码 hash 见本地 `work/server-capacity-212-report.json`；可重现脚本是 `work/isolated-capacity-212.mjs` 和 `work/run-remote-capacity-212.py`。

不能据此承诺“能承载 50 个公网用户”。页面常驻但不操作、同时同步、同时密码登录、同时整理长通知是不同负载。模型速度、带宽、通知长度、保留量和共享校园网络都会改变结果。

## 模型入口与比赛演示

当前整理为单通道，一次只执行一个没有缓存的新模型请求；繁忙时先拒绝，保留用户输入，不排队占用无限内存，也不自动收费重试。常规读取、云同步和查看已有通知不需要等待模型结束。

当前默认防护：每日全站最多 30 次实际模型请求、保守成本预算 3 元；每账号每日 10 次、每网络每日 10 次，失败的实际调用也消耗预算。相同原文短时间缓存可复用，读取和缓存复用不增加模型费用。这些是防费用失控的运营限制，不是硬件极限。内网负载测试没有更改生产预算。

比赛建议先以十至二十人分批试用，实际 AI 整理由一个演示者操作；其他人可同时浏览脱敏示例、勾选、看出处和已有整理结果。演示前准备好账号，避免多人共用校园出口时碰到邀请码或邮件注册限额。共享同一公网 IP 的真实整理总量还可能先到每日十次限制。不要为现场演示直接取消日预算、防护或开放管理权限。

扩容前先看真实统计：失败类别、模型繁忙次数、预算耗尽、SQLite 文件及剩余磁盘、进程内存、备份状态。若逐步出现长期排队，再增加有界队列与单账号公平调度；若持续数据库负载超过单机能力，再考虑独立数据库服务。多台 Node 不能直接共享本机 JSON 预算账本与 SQLite 文件来绕过单进程限制。

## 文字存储

本次 854 字的虚构通知正文为 2,474 UTF-8 字节，代表 v5 通知 JSON 约 3,060 字节。若一万条都同样长，单份通知正文结构约 29.2 MiB；这是样本算术估计，不是所有真实通知的平均值。长通知、多个主题、任务步骤、出处和人工纠错会明显增大体积。

目前逻辑上限：

- 单条云通知 64 KiB；每账号最多 1,000 条有效通知、5 MiB 通知文字，以及 5,000 个历史编号（含删除标记）。
- 整理任务保留原文与结果，每条最多 512 KiB；每账号最多 1,000 个任务、10 MiB 任务数据。
- 全站通知内容最多 256 MiB、任务内容最多 256 MiB；账号数目前最多 500。
- 每页同步最多 100 条、约 512 KiB，每次上传最多 100 项／1 MiB；附件二进制留在本机，不上传这些 SQLite 文字空间。

通知和整理任务可能各存一份原文，不能只算一份正文。上述是程序统计的内容字节，**不是数据库文件占用的硬盘上限**：索引、删除标记、SQLite 页面、WAL、空闲页、程序版本和备份还会占空间。本次隔离数据库及 WAL 约 3.91 MiB / 126 条有效通知，主要包含短突发事务日志，不能把这个比例当成永久每条通知大小。

容量不足会明确拒绝新写入，不清空旧通知；已得到的 AI 合法结果可保留快照，免费重试保存。长期达到账号或全站上限时，应先备份和联系维护者，下一步再设计用户主动归档／清理流程，不能自动删除原文、笔记、进度或已有备份。

## 云同步与关闭边界

云端使用 WAL；通知写入采用 `synchronous=FULL` 事务，编号和版本比较防止旧客户端覆盖新记录。变更、冲突及分页都有明确结果，删除是有版本的标记。账号与通知是两个 SQLite 文件，不是跨数据库的单个事务。

后台整理先持久保存原文、任务编号与预算，收到 202 确认后后台继续，合法结果保存到任务快照和用户同步空间。关闭页面不会取消已经确认的后台模型任务；重新打开可按编号查询，进程意外中断则保留原文并标失败，不自动再次收费。

普通编辑先落本机，上传受前端同步调度影响。关闭前若还没收到云端确认，本机数据仍在，但不能承诺另一设备立刻可见。页面隐藏或退出时只能尽力发小请求；浏览器被系统强杀、离线或电量耗尽仍可能阻止发送。应以页面“已同步”或任务“已接收”状态作为云端确认，而不是等待一个固定秒数。

## 备份与恢复

新增备份脚本采用 SQLite online backup，再压缩副本，原数据库只读；每份检查数据库完整性。快照属于逐数据库一致快照，**不是账号、同步数据、用量三个文件的跨库原子快照**。若需要对所有库做严格一致的灾备恢复，应在维护窗口停止写入后操作，先在隔离目录验证，再经用户明确许可恢复正式数据。

定时器设计为每天 UTC 03:15（上海 11:15），加最多三十分钟随机延迟，机器恢复后补执行。默认备份总额 512 MiB，达到上限报 `BACKUP_CAPACITY`，不自动删除旧备份或用户数据。后台只显示备份状态、尝试／成功时间、体积和有限错误类别，不返回路径、原文或错误日志。定时器实际启用与最近成功时间需发布后独立核对。

本地免费恢复验证使用 12 个虚构账号、100 条虚构通知和任务，压缩副本还原后各表全部内容、用量 JSON 与原库一致；空间不足时原文件和旧快照保持，保留上次成功时间。恢复报告在 `work/backup-recovery-212-report.json`。检查还发现并修复了连接未显式关闭造成的备份侧文件，以及未计入元数据的容量开销；最终紧贴限额时安全拒绝、超额零字节，备份目录为 0700、文件为 0600。初次完成报告单独保存在 `work/backup-recovery-212-before-fix-report.json`。私密配置不随这些数据库备份上传，恢复时还需保持原签名配置与部署凭据的安全管理。

单机备份能应对误操作或数据库损坏，但整台服务器或磁盘丢失时，同盘备份也可能丢失。后续如需要异地备份，应单独配置受控加密副本及访问权限；当前没有新建付费存储或宣称已做异地灾备。定期在临时目录恢复检查，并人工处理备份容量提示。
