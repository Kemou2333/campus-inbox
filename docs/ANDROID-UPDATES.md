# 安卓直接检查最新正式版本

新版一次检查指向**当前最高已批准正式版本**，不要求先安装所有中间版本。实际安装仍由用户在系统界面确认，沿用原包名及签名；它不是自动下载、自动安装或后台常驻服务。

## 本次问题的真实原因

已只读核对GitHub标签`android-v2.25.1`与`android-v2.26.0`中的`NativeUpdates.java`及`NativeUpdatePolicy.java`：两版实现相同。

旧`checkOnEntry`在开始网络请求前，先将SharedPreferences里的旧`cachedRelease`回调给界面。假如手机2.25.1曾经保存2.26.0的结果，就会先弹出2.26.0。即使本轮网络随后查到更新版本，Activity的同次进入/弹窗守卫也可能阻止第二个提示。因此用户看到逐级提示；数值版本比较本身并没有要求逐级安装。

旧手动`checkNow`也不是始终绕过缓存：`lastSuccess`不足30秒时直接复用已存结果，之后才再次联网。旧版只请求固定的`https://api.github.com/repos/Kemou2333/campus-inbox/releases/latest`，完全不读取阿里云更新清单。

**已装旧APK的这段行为无法靠远程替换阿里云JSON修复。**不清空手机应用数据，也不改写旧Release、标签或同名APK来伪装最新版本。

旧版用户无需逐级安装：取消旧提示后，直接打开当前正式最新版的精确APK链接（阿里云验证页或同版本GitHub备用），由系统同签名覆盖安装即可。联网正常时也可在上一次成功检查30秒后通过设置再次检查；但这依赖旧版能访问GitHub，不能保证其首次旧缓存提示消失。

## 新客户端行为

- 自动检查先联网；只在本轮公开端点返回有效结果后提示，取消联网前的旧缓存弹窗。
- 手动检查始终尝试本轮验证，不再以近期`lastSuccess`直接返回旧版本；同一在途检查合并，高频点击仍有30秒频控。失败明确返回失败，自动检查失败保持静默，不把离线缓存称作“最新”。
- 主元数据为固定的`https://123.57.30.129/downloads/android-latest.json`。服务端从只读已批准资产索引选最高数值正式版本；目录更新后即生效，不依赖APK内置网页或静态站CI何时完成。
- 主元数据不可用、非法或落后时，唯一备用仍是固定的GitHub最新正式Release API。拒绝草稿、预览、无匹配已上传APK或任意第三方下载地址。
- 两来源都拒绝比已安装版本或已知有效版本更旧的元数据，避免通道回退又覆盖成中间版本；有效同版本结果才可标为当前版本。
- 禁用URL响应缓存并请求重新验证。304仅允许复用由当前应用版本、当前缓存格式、同一精确端点验证过的ETag；旧GitHub/旧静态清单的ETag不迁移到新端点。旧缓存可用于判断响应是否回退，不可在网络完成前直接触发提示。

两个固定来源均保留系统HTTPS校验、禁止自动跳转、响应体大小上限（主32 KiB/备用512 KiB）、每次连接和读取最多3秒及约14秒总期限，不接受网页传入另一个更新服务器。

更新清单必须同时给出匹配版本的GitHub精确APK链接。有效阿里云地址优先，GitHub为备用；两种链接保持现有精确来源/路径约束，不接受userinfo、附加参数、编码别名或另一个版本。版本发现本身不消耗AI次数或APK下载字节额度，实际阿里云文件下载仍需图形验证码和独立流量预留。

## 发布与验证边界

发布流程应先验证同签名稳定APK及精确GitHub资产，再原子更新阿里云已批准资产索引；不把候选或预览写入索引。静态`android-download.json`继续服务网站和兼容客户端，但不决定新版原生最新版本查询。不得删除旧Release来纠正手机缓存，也不使旧文件名实际返回别的版本。

本次用GitHub只读核对旧源码与当前最新Release，未修改Release或标签。纯Java边界检查补充跨多个版本、数值比较、拒绝回退、旧缓存/跨来源/升级后ETag失效等情况；独立元数据由本地HTTP测试覆盖GET/HEAD、数值最高版本、热读、零账本写入与坏索引。编译/本机HTTP检查不等于旧手机升级、系统安装或真实网络验收。
